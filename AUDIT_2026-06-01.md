# Data audit — 2026-06-01

Goal: make every pooled estimate provably correct, validated two ways
(internal consistency per measure; comparison to published meta-analyses).

## Method 1 — cross-validate vs R metafor (gold standard for binary/count data)
Compared the Python/JS pool against the 731 R `metafor` sidecars (REML+HKSJ).
Initial: only 49% agreed within 15% — 335 apps showed a DIRECTION FLIP
(Python pooled OR>1, R pooled OR<1 on the same trials).

Root cause: the apps' JS engine and the Python validator pool from
`publishedHR`, but **228 trials in 192 `_AUTO` apps had a publishedHR that
contradicts its own raw 2x2 counts in direction** (e.g. ADALIMUMAB_PSA HR=7.08
vs count-OR 0.142 = 1/7; ANDEXANET HR=73.8 but 1/14 treated vs 26/27 control).
The publishedHR was inverted/mis-extracted; the raw counts are clinically
correct and match R. **Fixed: nulled those publishedHR so pooling falls to the
correct counts.**

Key nuance (why "counts-first everywhere" is WRONG): for the curated
time-to-event benchmark apps the published **HR is the correct estimand** and
the count-OR is a poor proxy (tested: HR-first keeps 17/17 benchmarks,
counts-first only 9/17). So pooling stays **estimandType-aware / publishedHR-
first**; the fix only removed publishedHR values that were internally
contradicted by their own counts.

## Method 2 — internal consistency per summary measure
Per estimandType (OR 2609, RR 963, HR 904, MD 815, RD 62 trials):
- direction vs counts (OR/RR): 0 violations (after fix)
- CI ordering (lo<est<hi): 0 violations
- effect-within-CI: 0 violations
- non-positive ratio / CI bound (impossible for a ratio): nulled in 397 apps
  (these were misplaced mean differences or extraction artifacts)
Residual (flagged, not pool-breaking): ~59 OR/RR trials whose value diverges
>3x from the count-OR — mostly measure-labeling (a RR labelled OR, e.g.
BIMEKIZUMAB PASI90 17.6 ~= 85%/4.8% RR) or an outcome mismatch (the counts are
a different endpoint than the published effect). Pool uses the published effect
so these are data-cleanliness, not wrong pools. Logged for source review.

GLP1_CVOT 0.86 vs 0.88 (Sattar 2021 IPD), PCSK9 0.85 (Guedeney 2020),
SGLT2_CKD/ARNI_HF/ABLATION_AF/RIVAROXABAN/ATTR_CM/INTENSIVE_BP/INCRETIN/
MAVACAMTEN exact; DOAC_CANCER_VTE 9.1%, COLCHICINE 4.7%, IV_IRON 3.6%,

Caveat (per reviewer): published metas can differ in k / inclusion criteria —
e.g. TEZEPELUMAB app k=1 (NAVIGATOR) vs a 2-3 trial published basis.

## Method 1b — MEASURE-AWARE cross-check vs R metafor (resolved)
The naive check pooled count-OR for every app, wrongly penalising HR apps.
Re-ran metafor (REML+HKSJ) on each app's ACTUAL pooling inputs — publishedHR
effects for HR/ratio apps, OR-from-counts for binary, md/se for MD — via
scripts/poolcheck_metafor.R over outputs/poolcheck_input.json.

True agreement (Python DL vs R metafor REML, same inputs per measure):
  OR  96% (627/42/29)   RR  97%   HR  100% (133/0)   MD  98%   RD  100%
  ALL 97% within 15%; **0 direction flips**.
The 36 residual diffs are 33/36 high-I^2(>=75%) and 31/36 small-k(<=4) —
i.e. legitimate DL-vs-REML divergence, not data errors. REML keeps 19/19
benchmarks. (Validator pools DL for speed; apps + sidecars use REML+HKSJ.)
